# Packaging implementation

## Convergence boundary

`vulcan-app/electron/installCoordinator.cjs` runs the platform repair script on every packaged launch. Each script reports its terminal state with a `VULCAN_RESULT=<json>` line so Electron can distinguish successful repair, Docker-group relogin, WSL reboot, and a missing macOS Homebrew prerequisite. On Linux, first-run installation remains in the Electron process the user originally launched; the installed AppImage is used by later launches rather than forcing a mid-startup restart.

The bundled server payload has a deterministic SHA-256 generated by `vulcan-app/scripts/generate-runtime-hash.mjs`. The Python runtime is rebuilt only when the payload hash changes or its import health check fails.

Visible packaged launches keep the main Vulcan renderer uncreated while convergence is running. If repair lasts longer than 400 ms, Electron presents a compact 560×124 setup surface instead: a full-width green indeterminate barber pole, live setup stage text, and a `Click for details` control. Details expand the same native window to 560×300 and show per-stage state plus the installer process's live stdout/stderr. Once convergence succeeds the setup surface closes and the real Vulcan window is created. Healthy fast launches never flash the setup UI, and `--hidden` login startup keeps it hidden unless the user explicitly opens Vulcan during repair.

## Linux

The AppImage is built with electron-builder's static AppImage runtime (`toolsets.appimage = 1.0.2`), so launching Vulcan does not require host FUSE2 support. Its embedded desktop entry also sets `X-AppImage-Integrate=false`: Vulcan owns its own install/update integration and AppImageLauncher must not move or reintegrate the artifact.

The AppImage is copied atomically to `~/.local/share/vulcan/app/Vulcan.AppImage`. The launching AppImage continues as the user's first Vulcan session; the persisted copy is used naturally by later app-menu launches. Desktop metadata is written under the user's XDG directories. Vulcan-owned server state — including its managed uv/Python runtime and persisted packaged server payload — lives alongside conversations and workspaces under `~/.vulcan`. Docker is reused when healthy; on Arch the missing-engine path is `pacman -S docker`, while other Linux hosts use Docker's installation script. Privileged host operations use Polkit (`pkexec`).

The Vulcan server is supervised by `~/.config/systemd/user/vulcan.service` and executes `vulcan serve`, a foreground service entry point added to the server CLI.

## Windows

NSIS installs the Electron application. Etna remains native to Windows and is discovered or repaired through its public CLI. Vulcan's managed Python/server runtime and Docker live inside the dedicated WSL2 distro named `Vulcan`. The installer verifies or repairs that Ubuntu 24.04 substrate, then delegates backend convergence to the same Linux converger used elsewhere. All WSL commands target `-d Vulcan`; existing user distros are untouched.

If Windows has just enabled WSL2 and requires a reboot, repair exits cleanly. Opening Vulcan after reboot resumes from observed state.

## macOS

Electron uses `app.moveToApplicationsFolder()` for the native `.app`. Etna remains native to macOS while Vulcan's managed Python/server runtime and Docker live inside the named Colima profile `vulcan`. This keeps Playwright and other client-POV Etna tools attached to the real host browser. A small host uv bootstrap exists only as an Etna installation fallback. Homebrew is required only when Colima itself is absent. Healthy Colima and LaunchAgent state are skipped; the Linux guest converger owns Vulcan backend repair. Colima/Lima owns VM lifecycle and localhost port forwarding.

## Desktop lifecycle

- window close -> hide to tray without suspending renderer transport
- hidden/minimized Electron -> General WS proof-of-life and client-POV provider/Etna relays remain live
- tray Open -> show/focus
- tray Exit -> quit Electron
- server remains independently supervised
- completion/error push -> native Electron notification when Vulcan is not focused
- notification click -> focus Vulcan and select the corresponding chat
- Windows/macOS -> Electron login-item startup with `--hidden`
- Linux -> XDG autostart entry with `--hidden`

## Direct Linux bootstrap from GitHub

The repository-root `install.sh` also acts as the public desktop bootstrap.

    curl -fsSL https://raw.githubusercontent.com/dwhite-sys/vulcan/main/install.sh | bash

It downloads the stable `Vulcan.AppImage` release asset, obtains its SHA-256 from GitHub release metadata, verifies the download, atomically installs it at the normal Vulcan AppImage location, and launches it. The packaged application's embedded converger owns backend repair on that launch and every later launch.

The release publishes stable aliases `Vulcan.AppImage`, `Vulcan-Setup.exe`, and `Vulcan.dmg`. Their SHA-256 values are included in the GitHub release body; standalone bootstrap code also accepts GitHub's per-asset digest when the API supplies one. Separate SHA-256 sidecar assets are not required.

## Headless / `--server-only`

The repository-root installer also supports a desktop-free desired state.

    curl -fsSL https://raw.githubusercontent.com/dwhite-sys/vulcan/main/install.sh | bash -s -- --server-only

The bootstrap resolves the selected release tag, downloads GitHub's source tarball for that exact tag, and delegates to that tagged installer with only the Vulcan server package. Electron and desktop integration are never installed.

Native Linux server-only mode uses `/etc/systemd/system/vulcan.service`, so the Vulcan backend starts at boot and survives SSH logout. Etna remains separately host-owned: Vulcan uses Etna's public CLI only when setup or repair is required and does not install a private Etna runtime, run a second Etna process, or manage Etna's service lifecycle.
